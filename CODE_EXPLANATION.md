# Как объяснить Brickfall на защите

Я сделал Breakout: игрок двигает платформу и отбивает мяч.
Нужно разбить кирпичи и пройти три уровня.
Есть три жизни, две специальные механики, регистрация, сохранение и рейтинг.

## Как запускается программа

Сначала я запускаю сервер:

```powershell
.\.venv\Scripts\python.exe -m uvicorn api.main:app --host 127.0.0.1 --port 8000
```

Потом запускаю игру во втором терминале:

```powershell
.\.venv\Scripts\python.exe -m client.main
```

Ключ `-m` запускает модуль Python из папки проекта.
Сервер создаёт таблицы в SQLite, если их ещё нет.
Клиент открывает окно Pygame и главное меню. При выборе новой игры
без входа появляется экран регистрации и входа.
Сайт открывается в браузере по адресу `http://127.0.0.1:8000`.

## Почему код разделён на папки

В `game/logic.py` находятся правила игры: движение, столкновения,
жизни, очки, уровни и таймеры. Здесь нет `import pygame`.
Игровая логика оперирует числами и прямоугольниками.

В `client/` находятся окно, клавиатура, кнопки и отрисовка.
Клиент вызывает методы игры и показывает получившееся состояние.
`client/api_client.py` отправляет запросы на сервер.
Он использует стандартную библиотеку `urllib`.

В `api/main.py` описаны адреса сервера.
В `api/db.py` находятся SQL-запросы.
Pygame не читает базу напрямую.

## Как устроен игровой цикл

Pygame повторяет три действия: читает события, обновляет логику и рисует кадр.
Время между кадрами называется `dt` и измеряется в секундах.
Если игра на паузе, расчёты движения и таймеров не выполняются.
Кнопки и меню при этом продолжают работать.

У игры есть состояния, например игра, пауза, победа и поражение.
По ним клиент понимает, какой экран рисовать и какие действия разрешены.
После поражения или победы можно начать новую попытку.

## Как движется мяч

У мяча есть координаты `x`, `y` и две составляющие скорости:
горизонтальная и вертикальная. За небольшой промежуток времени:

```python
x = x + speed_x * dt
y = y + speed_y * dt
```

Если мяч летит в стену, меняется знак соответствующей скорости.
При ударе о боковую стену меняется горизонтальная скорость,
при ударе о верхнюю — вертикальная.

У платформы есть скорость движения и границы поля.
За границы она не выходит.
Перед запуском мяч стоит на платформе и перемещается вместе с ней.
Space запускает мяч. После потери жизни нужно снова нажать Space.

## Как определяются столкновения

Кирпичи и платформа описаны прямоугольниками.
Для мяча известны центр и радиус.
Логика проверяет, касается ли мяч границ прямоугольника.

Движение разбито на маленькие шаги, чтобы быстрый мяч не пролетал
сквозь тонкий кирпич между кадрами.
После столкновения мяч выводится за границу препятствия
и отскакивает. Это помогает избежать застревания и повторного удара
по одному препятствию.

Кирпич удаляется при попадании, к счёту прибавляется 10.
При отскоке от платформы учитывается место попадания:
ближе к краю мяч летит сильнее в сторону.
Мяч отбивается платформой, когда летит вниз.

## Три уровня и жизни

Для каждого уровня создаётся своё расположение кирпичей.
Скорость мяча постепенно растёт.
Когда кирпичей не осталось, начинается следующий уровень.
После третьего уровня появляется победа.

Если мяч падает ниже платформы, количество жизней уменьшается.
При оставшихся жизнях мяч возвращается на платформу.
Если жизней нет, появляется экран поражения.
Очки сохраняются между уровнями одной попытки.

## Сужение платформы

Счётчик запоминает число уничтоженных кирпичей за всю попытку, включая прошлые уровни.
После каждых пяти включается таймер на три секунды.
Пока таймер больше нуля, ширина платформы уменьшена.
Каждый игровой шаг уменьшает таймер на прошедшее время.
Когда он заканчивается, возвращается обычная ширина.

## Замедление мяча

В начале уровня доступно одно замедление.
Если нажать Shift, когда мяч уже летит, включается таймер на три секунды.
Во время действия механики мяч движется медленнее.
После окончания таймера возвращается обычная скорость.

После использования заряд заканчивается до следующего уровня.
Потеря жизни не возвращает заряд.
До запуска мяча заряд не расходуется.
На паузе оба таймера остановлены.

## Шрифты и размер окна

Для обычного текста я загружаю файл Segoe UI Regular, для заголовков и кнопок —
Segoe UI Bold. Поиск SysFont раньше выбирал Light, поэтому текст был слишком тонким.
Сглаживание включено при отрисовке текста.

Логика и интерфейс используют поле 900×600. Функция present() масштабирует
его под окно с сохранением пропорций. game_position() переводит координаты
мыши обратно, поэтому кнопки работают и после изменения размера.

## Что такое SQLite

SQLite — база данных, которая хранится в одном файле.
В Python для неё есть встроенный модуль `sqlite3`.
Мне не нужен отдельный сервер базы данных или тяжёлая библиотека ORM.

Таблица `users` хранит пользователей и данные для проверки пароля.
`sessions` связывает хеш токена с пользователем и сроком действия.
`scores` хранит завершённые попытки.
`saves` хранит одно последнее сохранение каждого игрока.

Идентификатор пользователя связывает его строки в разных таблицах.
Уникальное имя не позволяет зарегистрировать один аккаунт дважды.
Пара `user_id` и `run_id` уникальна в результатах.

SQL-запросы используют параметры `?`, например:

```python
database.execute("SELECT * FROM users WHERE username = ?", (username,))
```

Имя передаётся отдельно от SQL, поэтому введённый текст не становится
частью SQL-команды. После работы соединение закрывается.
Успешные изменения сохраняются, а при ошибке отменяются.

## Что такое API

API — набор адресов, по которым программы обмениваются данными.
В моём проекте это HTTP-запросы с JSON.
JSON хранит обычные поля: строки, числа, списки и словари.

Например, клиент отправляет `POST /login` с именем и паролем.
Сервер проверяет данные и возвращает ответ.
Код 200 означает успех, 201 — создание записи, 400 — неправильные данные,
401 — требуется вход, 404 — запись не найдена,
409 — конфликт, например занятое имя.

## Как работает регистрация

Сервер проверяет имя и длину пароля.
Имя состоит из 3–20 латинских букв, цифр, `_` и `-`.
Пароль должен содержать от 8 до 128 символов.

Для нового пароля создаётся случайная соль через `secrets`.
Из пароля и соли вычисляется PBKDF2-хеш через `hashlib`.
В базу попадают соль и хеш, а сам пароль не сохраняется.

При входе сервер повторяет расчёт с сохранённой солью
и сравнивает хеши. При неправильном пароле возвращает 401.

При переключении между входом и регистрацией поля не очищаются.
После успешного POST /register клиент сразу делает POST /login с теми же данными
и получает обычный токен. Затем можно выбрать New game.
Ошибка 409 означает, что имя уже занято: форма предлагает войти.
Если пользователь закрыл форму, поздний ответ запроса её больше не открывает.

## Зачем нужен токен

После входа сервер создаёт случайный токен.
Клиент отправляет его в заголовке `Authorization: Bearer ...`.
Так сервер понимает, кому принадлежат очки и сохранения,
без повторной передачи пароля в каждом запросе.

На сервере хранится хеш токена и срок действия, а у клиента токен
остаётся только в памяти. После закрытия приложения нужно войти снова.
Токен действует семь дней; чужие сохранения через него недоступны.

## Как отправляются очки

После победы или поражения клиент берёт итоговый счёт
и идентификатор попытки `run_id`.
Он отправляет их через `POST /scores` с токеном.
После ответа показывает, удалось ли сохранить результат.

Клиент запоминает успешную отправку и не повторяет её автоматически.
Уникальный `run_id` в базе дополнительно защищает от дубликатов.
Если ответ потерялся, повторная отправка той же попытки
не увеличит число сыгранных игр второй раз.

Сетевые действия выполняются отдельно от отрисовки.
У запроса таймаут три секунды.
При недоступном сервере появляется понятное сообщение,
а приложение остаётся открытым.

## Как сохраняется игра

`Game.to_dict()` собирает состояние в обычный словарь.
В него входят уровень, очки, жизни, кирпичи, мяч, платформа,
таймеры и `run_id`.
Клиент отправляет словарь через `PUT /saves`.
Сервер проверяет его и сохраняет как JSON в SQLite.

Для загрузки клиент вызывает `GET /saves`.
Метод `Game.from_dict()` проверяет значения и восстанавливает игру.
Отсутствующее сохранение даёт 404, а неправильное состояние отклоняется.
Сохранение находится на сервере, поэтому остаётся после закрытия клиента.

## Как сайт получает результаты

Маршрут `/` вызывает функцию базы с SQL-запросом.
Запрос группирует попытки по игроку и выбирает `MAX(score)`.
Затем сортирует по убыванию счёта и берёт первые десять строк.
Один игрок занимает только одно место.

FastAPI передаёт строки в шаблон Jinja2.
Цикл в HTML создаёт строки таблицы.
Если список пуст, шаблон показывает сообщение.
Выдуманных результатов в коде нет.

Страница профиля получает количество игр через `COUNT`,
лучший результат через `MAX`, средний через `AVG`.
Данные сайта и игры находятся в одной базе.

## Как работает Git и Docker

Git хранит историю изменений. Коммит — сохранённый этап работы.
`git status` показывает изменённые файлы,
`git add` подготавливает их, а `git commit` создаёт коммит.
`git fetch` получает информацию об удалённой ветке,
`git push` отправляет локальные коммиты на GitHub.
`.gitignore` исключает базу, окружение, кеши и секреты.

Docker собирает окружение сервера по Dockerfile.
Compose открывает порт 8000 и подключает постоянный том SQLite.
Pygame запускается отдельно, потому что ему нужно окно на компьютере.
Здесь Docker не установлен, поэтому реальный контейнер не запускался.

## 15 вопросов преподавателя

1. **Почему Python?** Он понятный, а Pygame позволяет сделать небольшую 2D-игру.
2. **Почему game и client разделены?** Чтобы расчёты не зависели от окна и их можно было проверить отдельно.
3. **Зачем нужно время dt?** Чтобы скорость движения не зависела напрямую от количества кадров.
4. **Почему мяч меняет направление?** При столкновении меняется знак нужной составляющей скорости.
5. **Как мяч не пролетает сквозь кирпич?** Движение рассчитывается маленькими шагами.
6. **От чего зависит угол отскока платформы?** От расстояния попадания до центра платформы.
7. **Чем отличаются уровни?** Расположением кирпичей и большей скоростью мяча.
8. **Как работают три секунды механики?** Таймер уменьшается на время игрового шага, а на паузе стоит.
9. **Что хранится в SQLite?** Игроки, хеши паролей, сессии, результаты и сохранения.
10. **Почему нельзя хранить обычный пароль?** Тогда при утечке базы его сразу увидят; вместо пароля хранится хеш.
11. **Для чего соль?** Она делает хеши одинаковых паролей у разных игроков разными.
12. **Для чего токен?** Он подтверждает вход и связывает запрос с нужным пользователем.
13. **Как избежать двух одинаковых результатов?** У попытки есть уникальный run_id, а база не разрешает его дублировать.
14. **Как получается топ-10?** SQL берёт лучший счёт каждого игрока, сортирует и ограничивает список десятью строками.
15. **Зачем Git и .gitignore?** Git хранит историю кода, а .gitignore исключает временные файлы, базу и секреты.
